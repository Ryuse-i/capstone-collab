# PSU-Collab Role-Aware Onboarding Guide — Implementation Plan

## 1. Summary

PSU-Collab already has role-based routes and dashboard variants, but it does not have a tour, stable tour targets, or persistent onboarding state. The earlier scan found useful features and several real copy/navigation problems, but it missed a routing gap: a student with no project currently lands on a “not assigned” screen rather than the existing Get Started screen. Build one small, route-aware tour with role-specific steps, stable `data-tour` targets, local per-user completion/skip state, and a replay action in the account menu. Before the new-student and invited-member tours, fix the no-project route and invitation return/refresh flow; keep backend persistence out of scope unless cross-device tracking is a firm requirement.

## 5. Library recommendation

No tour library is currently listed in [`frontend/package.json`](../frontend/package.json). Bundle sizes below are relative planning estimates only: the repository has no package installed and no measured bundle comparison.

| Option | Stack fit | Bundle / implementation cost | Accessibility considerations |
|---|---|---|---|
| Driver.js | Framework-independent DOM targeting can work with React pages; a small React-side controller must handle React Router navigation, query readiness, and role conditions. | Expected low incremental size and low setup effort; exact installed/gzipped size is **Unverified** until measured with Vite. | Do not assume the default popover/overlay is sufficient. Verify focus movement and restoration, keyboard operation, names/descriptions for screen readers, zoom, and reduced motion. |
| Shepherd.js | Flexible multi-step tours and lifecycle hooks; more configuration and styling integration than the first release needs. | Expected higher package/configuration overhead than Driver.js; exact incremental size is **Unverified** in this project. | Validate focus and keyboard behavior across route transitions; added customization can create extra accessibility work. |
| Custom React overlay using existing UI primitives | Fits React Router and can reuse the project’s existing Radix-based dialog/popover primitives. | Lowest third-party bundle cost, but highest engineering and maintenance cost; the team must build spotlight positioning, resize/scroll behavior, and route lifecycle handling. | Best control only if the team implements and tests complete keyboard, focus, semantic, and screen-reader behavior; not automatically accessible just because Radix is used. |

**Recommendation: Driver.js for the first version**, behind a small app-owned tour controller. It is the simplest way to get a guided spotlight without building a positioning engine, while the app controller retains responsibility for role detection, navigation, target readiness, persistence, and accessible behavior. Before merging the dependency, compare the production Vite output and run keyboard/screen-reader checks. If Driver.js cannot meet the acceptance checks without extensive overrides, use a custom Radix-based overlay rather than layering more dependencies.

## 6. State and persistence

Use browser `localStorage` for durable “completed” and “skipped” decisions, scoped to a user and tour version. Keep current step and route-transition state in memory only; if the tab closes during a tour, restart that tour on explicit replay rather than restoring a stale spotlight.

| State | Recommendation |
|---|---|
| Completed | Save `{ status: "completed", version, completedAt }` under a key such as `psu-collab:onboarding:v1:<userId>:<tourId>:<projectId-or-global>`. Write only after the final step or an explicit completion action. |
| Skipped | Save `{ status: "skipped", version, skippedAt }` under the same scoped key. A skip suppresses automatic re-opening but must not remove the Help replay action. |
| Per-step progress | Keep in provider memory for the active session; do not persist a half-open step number. Query and target conditions can change between visits. |
| Cross-device | Local storage does not sync. This is acceptable for the first release if onboarding is a convenience rather than a compliance requirement. If cross-device completion is required, add an authenticated user-preference/API field or a small onboarding-state resource and an Alembic migration; update the user schema, service, routes, and frontend query types. No such field exists on the current [`User` model](../backend/app/modules/users/model.py). |
| Logout / account switch | Keep records on logout, but namespace all keys by immutable user ID so another account on the same browser does not inherit the prior account’s progress. On storage failure, run the tour in memory and do not claim it was saved. |
| Role change | Re-fetch the current user and active project membership before automatic launch. Use a distinct `tourId` for each role variant; a new role therefore gets its applicable tour, while the old role’s state remains stored but dormant. |
| New project / second project | Include project ID in project-specific leader/member keys. Do not start for a second project until the UI can identify that project as active; queue an invitation-triggered request rather than spotlighting the first project returned by the current lookup. |
| Version changes | Increment the tour version when step order or core guidance changes. Keep the replay action available regardless of version/status. |

This design needs no backend/database changes. Do not store names, email, invite tokens, task contents, or other project data in onboarding state.

## 7. Entry points

- **Automatic start:** after successful authentication, resolve `/users/me`, project membership, and project data; then start only the matching unseen tour on `/dashboard`. `GuestRoute` and the login/signup forms already navigate to the dashboard, but current signup/login navigation does not encode onboarding state. See [`GuestRoute.tsx`](../frontend/src/components/GuestRoute.tsx), [`login-form.tsx`](../frontend/src/components/login-form.tsx), and [`signup-form.tsx`](../frontend/src/components/signup-form.tsx).
- **Project setup start:** after the no-project routing fix, show the student setup tour on the no-project dashboard. After project and leader membership are confirmed, offer the separate leader tour; do not chain-open it on top of the setup dialog.
- **Invited-member start:** set a short-lived pending-tour intent only after either invitation acceptance mutation succeeds; refresh membership/project queries first. For a link, the result includes project ID and role; for email invitation, use the accepted invitation response. See [`useInviteLink.ts`](../frontend/src/hooks/useInviteLink.ts) and [`useProjectInvite.ts`](../frontend/src/hooks/useProjectInvite.ts).
- **Replay:** add **Replay onboarding guide** to the existing profile/account dropdown in [`nav-user.tsx`](../frontend/src/components/nav-user.tsx), which currently only provides Logout. Keep a second **Show setup guide** action in the no-project screen. A Help & Support label exists in the command dialog but does not currently invoke a help action; do not make that existing inert command the only replay path. See [`Applayout.tsx`](../frontend/src/layouts/Applayout.tsx).
- **Get Started screen:** replace the fake 0-of-3 progress checklist with a real, role-appropriate next-action card and a **Show setup guide** action. Do not add a backend progress model just to preserve a visual counter. The project setup tour itself communicates the three dialog steps.

## 9. Edge cases

| Case | Planned behavior |
|---|---|
| Mobile / small viewport | Use the library’s responsive placement where it fits; constrain popovers to viewport width and height, keep next/skip controls visible, and scroll the page target into view without forcing horizontal scrolling. If a target is obscured by the mobile sidebar or keyboard, skip that step with a clear message. Validate at narrow phone width and browser zoom. |
| Dark mode | Use the application’s theme tokens and contrast-safe overlay/popover styles; verify both Light and Dark. Do not hard-code the yellow/maroon colors from older custom UI where contrast is not checked. |
| Target missing, conditional, or still loading | Start only after the relevant route and query data resolve. Never target skeletons. Wait briefly for the exact selector; if absent, skip an optional step. If a required step is missing, end the tour with “This guide step is unavailable right now” and retain replay. Do not leave a dark overlay behind. |
| Route change during the tour | Keep controller state above page-level `AppLayout` instances (for example in `App.tsx`), because each page renders its own layout. Navigate only to known routes, wait for the next target, and cancel cleanly on browser Back, logout, or unmount. |
| Empty project / no assigned tasks / no instructor projects / empty admin list | Use an empty-state target and suitable explanatory copy, or skip the data-dependent step. Never treat “no records” as a failed load or as a completed task. |
| User skips | Persist “skipped” for the current role/tour version and project scope, stop immediately, and offer replay from the profile menu. A skip must not block navigation or appear as completion. |
| User joins a second project | Keep each project’s guide state separately. The acceptance handler knows the joined project, but the student current-project hook selects the first membership. Queue the second-project tour and do not show it until a project selector or reliable current-project contract is available. |
| Keyboard | All tour controls are real buttons with visible focus. Support Tab/Shift+Tab, Enter/Space, and Escape to exit; do not require pointer-only actions or keyboard arrow behavior. Restore focus to the launch control after completion/skip. |
| Screen reader | Give each popover dialog semantics, an accessible title/description, announced step count, and a clear relationship to its target; announce route/step changes. Keep the highlighted target reachable and avoid hiding the only copy of essential instructions in the overlay. Verify with a screen reader and automated accessibility checks. |
| Reduced motion / browser zoom | Respect `prefers-reduced-motion`; avoid animated spotlight movement when reduced motion is requested. Keep content usable at 200% zoom. |
| Logout, expired session, or role update mid-tour | Close overlay before auth redirect, do not persist partial progress, clear in-memory state, and recompute the role variant after the next `/users/me` result. Keep completed/skipped local records scoped to the prior user and variant. |
| Invite preview/acceptance failure | Do not mark the member tour pending unless acceptance succeeds. Preserve the existing invite error/expiry message and return the user to a usable page. See [`InvitePage.tsx`](../frontend/src/pages/InvitePage.tsx) and [`ProjectInviteNotification.tsx`](../frontend/src/components/notifications/ProjectInviteNotification.tsx). |

## 11. Testing and success measures

### Role test matrix

Use test accounts and realistic empty/non-empty data for each case. The current frontend package exposes `npm run build` and `npm run lint`; it does not declare a frontend test script, so plan for manual browser acceptance first and avoid introducing a new test framework solely for the tour. See [`frontend/package.json`](../frontend/package.json).

| Persona / fixture | Checks |
|---|---|
| Student with no project and no membership | `/dashboard` reaches setup (not the member empty message); tour waits for data; project fields validate; Skip and Replay work; creation success transitions to leader guidance only after membership is confirmed. |
| Student leader with a project | Leader tour appears once; invite control target is present only when rendered; task and workload steps resolve; missing recommendations are handled without an overlay error. |
| Student member accepted through email invitation | Accept notification, refresh project/member state, and start member guide once. Verify decline and invitation-loading states do not start a tour. |
| Student member accepted through a share link | Verify guest preview, login/signup return path, acceptance, correct project/role, query refresh, then member tour. Also verify expired/revoked/used-up invite states do not mark onboarding complete. |
| Instructor with zero and multiple projects | Empty state skips project detail; with multiple projects, the selected project is explicit and the guide never opens a stale/first project unintentionally. |
| Project advisor membership | Verify project-role advisor can follow staff guidance under the agreed platform role. If a platform advisor user is still intended, block release until backend/type/route behavior is reconciled. |
| Admin | Dashboard metrics, user search/create, and action-warning steps work; tour never invokes Reset password, Deactivate, or Remove. |
| All personas | Repeat after completion, skip, logout/login, account switch, role change, storage disabled, route Back, narrow viewport, dark theme, keyboard-only, reduced motion, 200% zoom, and screen-reader use. No step should cover or strand the target. |

### Measures

- **Completion rate:** completed tours divided by started tours, segmented by role and tour version.
- **Skip rate:** skipped tours divided by starts; inspect the step where users exit rather than treating a skip as failure.
- **First task created:** time from project creation/first leader tour start to the first project task.
- **Time to first submission:** time from member join/first member tour start to the first task submission.
- **Quality guardrails:** no increase in failed project/invite/task actions, no tours started for the wrong project/role, and successful keyboard and screen-reader completion.

Local-only storage cannot provide aggregate completion/skip analytics. For an initial small-team rollout, test a few users per role and collect task timing from existing project/task/activity data where available. Whether member activity provides a reliable timestamp for first submission is **Unverified**; confirm before using it as a metric. If the team needs ongoing aggregate completion/skip rates, explicitly approve a minimal first-party event collection mechanism with retention/privacy rules instead of adding a third-party analytics dependency by default.

Compare a small pilot with a no-tour baseline. Do not set a “good” completion or time target until the baseline and role sample sizes are known; a high completion rate alone does not prove that users successfully created or submitted work.

## 12. Risks and open questions

- **Advisor identity:** Is “advisor” only a project role under an instructor account, or should it be a separate platform account role? Current frontend/backend definitions disagree; the plan treats it as project-level until resolved. See [`roles.ts`](../frontend/src/constants/roles.ts) and [`users/model.py`](../backend/app/modules/users/model.py).
- **Multiple student projects:** Should students be able to belong to multiple projects and choose an active one? The current hook uses the first membership; second-project-specific onboarding depends on an active-project selection decision. See [`useProject.ts`](../frontend/src/hooks/useProject.ts).
- **Invitation permissions:** Should any project member be allowed to create/revoke role-bearing invite links, or only leaders? UI and backend service checks differ. See [`Dashboard.tsx`](../frontend/src/pages/student/Dashboard.tsx) and [`invite_links/services.py`](../backend/app/modules/invite_links/services.py).
- **Cross-device preference:** Is “completed/skipped” expected to sync across browsers/devices? The recommended first release is local-only; changing this requires backend API/schema and migration work.
- **Tour versus checklist:** This plan replaces the inert progress meter. If product owners require a persistent onboarding checklist, its milestones must be defined and tied to actual events before implementation.
- **Public signup/onboarding:** This plan starts guides after authentication. Confirm whether public landing-page guidance or account-creation walkthroughs are in scope; fixing the CTA/footer links is separate from the authenticated tour.
- **Submission payload:** Current submit action changes task status and the drawer has no notes/link controls. Confirm whether submission artifacts belong in a future feature; the guide will describe only the current status transition.
- **Analytics/privacy:** Is first-party aggregate guide measurement required? If yes, decide the minimum event fields, retention, and consent expectations before adding an endpoint/table.
- **Package accessibility and size:** Driver.js bundle output and assistive-technology behavior are not measured in this repository. Require a small spike and acceptance check before committing to the dependency.
